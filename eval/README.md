# 申请分析 Agent 模型对比实验

`model-ab.mjs` 是源码工作区的评测脚本，也已接入 EXE 的“模型 API 设置”页。完整基线实验用同一份冻结资料比较千问 Flash 和 DeepSeek Flash 的三层能力；候选实验只调用千问 Plus，并复用同输入哈希的历史 Flash/DeepSeek 输出，减少重复费用。

1. **项目集合筛选**：从 8 个候选项目中选出值得进一步分析的项目，记录临时人工参考集的召回率、精确率和是否覆盖全部候选决策。
2. **单项目分析**：覆盖案例丰富、案例较少、0 条案例、方向相近但不是直接匹配、量化/跨方向等项目，检查事实、引用、硬性条件和不确定性契约。
3. **整体排序与组合**：一次把 4 个项目交给横向校准器，检查是否全部覆盖、rank 是否唯一、中心值是否按 rank 单调、区间是否随证据量变化，并记录临时人工参考顺序的 Top1 和位移。

## 当前实验规模

完整基线实验是 30 次调用：

- 项目筛选：4 个场景 × 2 个模型 = 8 次；
- 单项目分析：8 个场景 × 2 个模型 = 16 次；
- 整体排序：3 个场景 × 2 个模型 = 6 次。

`node eval/model-ab.mjs` 只做离线预检，不联网。候选模式固定使用 8 个与基线输入哈希一致的场景（筛选 2、单项目分析 4、排序 2）；北京地域 `qwen3.7-plus` 价格按输入 ¥2、输出 ¥8/百万 token 做预检，脚本硬上限为 ¥5。该估算不是服务商账单；重复实验会重复产生费用。

## 成本记录方式

每个调用都会记录：

- 服务商、请求模型、层级、场景、提示词哈希、输入哈希和资料哈希；
- 请求字节数、输入 token、输出 token、总 token；
- 服务商返回的缓存命中 token（如果有）；
- 按未命中/公开峰时价格计算的保守费用估算；
- 按缓存命中价格计算的辅助费用估算；
- HTTP 状态、finish reason、耗时、原始模型输出和结构化解析结果。

运行时先按“最大输入估算 + 最大输出 token”做预算预检，超过预算就不发起请求。成功返回后再按服务商返回的 token 用量累计；如果服务商没有返回可核对的用量，脚本会停止后续调用，避免在无法对账时继续花费。

价格入口：[千问 Plus 官方价格](https://help.aliyun.com/zh/model-studio/qwen3-7-plus)、[千问 Flash 官方价格](https://help.aliyun.com/zh/model-studio/qwen-flash)、[DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。运行前应重新确认地域、峰谷、缓存和账户折扣。

## 如何运行

EXE 设置页候选实验固定使用 `qwen3.7-plus`，并与之前保存的 Flash / DeepSeek 基线对照。Key 使用 Electron 的 Windows 安全存储加密保存，评测子进程只通过运行时环境变量接收，不写入源码、实验 JSON 或日志。

如果在源码环境运行，也可以使用命令行：

```powershell
# 零费用：生成实验计划、检查固定样本、计算保守预算
node eval/model-ab.mjs

# 零费用：运行自动化回归
node --test eval/model-ab.test.mjs

# 零费用：预检 8 个候选场景和费用上限
node eval/model-ab.mjs --qwen-challenger

# 真实调用：使用千问 Plus，只调用 8 个场景，费用硬上限 5 元
$env:DASHSCOPE_API_KEY = "本机环境变量，不要写入仓库"
node eval/model-ab.mjs --run --qwen-challenger --max-cny=5
```

源码命令行运行后会在 `outputs/model-ab/<时间>-<随机标识>/` 写入；EXE 运行后会在本机软件数据目录下的 `model-ab/<时间>-<随机标识>/` 写入，完成时设置页会显示具体目录：

- `实验计划.json`：本次使用的场景、哈希、请求数和预算假设；
- `results.json`：逐次请求、原始输出、用量、费用、耗时和结构校验；
- `结果汇总.json`：按模型和 Agent 层级汇总调用数、通过数、累计费用、平均耗时和每个通过结果的费用；
- `人工评分表.csv`：按官方原文复核事实、引用、硬性条件和建议可用性。
如果只修改了本地校验规则，可以使用 `node eval/model-ab.mjs --recheck=结果目录` 对已保存的原始输出离线复核。它不会再次请求 API，会另存 `离线复核.json`，且不会覆盖当时的 `results.json`。复核只重算程序可接收性，不等于重新生成分析或事实验收。

## 结果怎么判

`referenceIds` 和 `referenceOrder` 是临时人工标注，不是真实录取标签。它们只用于发现“模型是否明显偏离产品预期”，不能据此宣称录取概率准确。

人工验收顺序：先排除 JSON/引用/硬性条件严重错误，再比较事实准确性、引用支持率、信息缺口、不确定性表达、筛选召回率、整体排序一致性、响应时间和费用。没有完成原文标注的指标保持待测，不填写推测数字。
评分表会单列明显不可能的名次表述（如“第 19 位，共 18 人”）；它只标记可自动识别的算术矛盾，不能代替人工事实核验。

该脚本是离线评测工具；当前桌面 EXE 的普通分析记录仍不等于这套 A/B 实验记录，不能把实验脚本新增的调用级字段描述成已上线埋点。
