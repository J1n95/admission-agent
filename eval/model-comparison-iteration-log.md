# 模型对比实验迭代记录

## 2026-10-16：从单项目 A/B 扩展到完整 Agent 流程

### 发现的问题

- 原评测只有 2 个单项目场景、4 次计划调用，只能观察项目分析输出，无法判断模型是否会把不相关项目筛掉。
- 原评测没有覆盖 Agent 的项目选择阶段，也没有覆盖多个项目放在同一把尺子上的排序阶段。
- 原记录有耗时和 token 用量，但没有把预算预估、缓存 token、逐次累计费用和停止原因放在同一条记录里。

### 本次判断

- 保留原有单项目分析，不删除用户真正需要的概率参考；增加项目集合筛选和整体排序两层。
- 使用同一份冻结申请资料、项目资料和提示词，只替换模型，记录 `promptHash`、`inputHash` 和 `dataHash`，避免把输入差异误判为模型差异。
- 质量指标拆成结构/契约指标与人工质量指标：程序自动检查 JSON、引用、硬性条件、覆盖和 rank；事实正确性、引用是否真正支持判断、建议是否有用仍由人工按官方原文评分。
- 将人工参考项目集和参考排序明确标为临时标签，不把它们当成真实录取标签或统计真值。

### 当前实验设计

- 项目集合筛选：4 个场景 × 2 个模型 = 8 次调用；记录临时参考集召回率、精确率和决策覆盖。
- 单项目分析：8 个场景 × 2 个模型 = 16 次调用；覆盖案例丰富、2 条案例、0 条案例、跨方向和量化方向。
- 整体排序：3 个场景 × 2 个模型 = 6 次调用；记录项目覆盖率、rank 唯一性、中心值单调性、区间宽度和临时参考顺序位移。
- 总计划：30 次调用；离线保守费用预估约 1.8141 元，预算上限 10 元。

### 成本与可追溯记录

- 每次调用记录服务商、请求模型、层级、场景、提示词/输入/资料哈希、请求大小、输入 token、缓存 token、输出 token、耗时、HTTP 状态和原始输出。
- 运行结束按“模型 × Agent 层级”生成调用数、结构通过数、累计费用、平均耗时和每个结构通过结果的费用，便于做成本/质量对比。
- 运行前用最大输出 token 做保守预算预检，超过上限不发起请求。
- 运行后按服务商返回 token 用量计算保守费用估算，并另存缓存口径费用估算；两者都不是服务商账单原值。
- 缺少 token 用量时停止后续调用，避免无法对账时继续消耗预算。
- 设置页增加千问/DeepSeek 双配置和一键运行入口；双模型 Key 沿用 Electron Windows 安全存储，避免要求用户在 PowerShell 中重复输入，也避免把密钥写进源码。

- 已验证：30 次计划构造通过；模型对比脚本测试通过；原桌面版测试和 50 条可靠性回归通过。
