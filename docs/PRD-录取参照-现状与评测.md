# 录取参照 PRD：现状、可信度与验证计划

> 文档快照：2026-10-14；对应当前工作区的 Windows 桌面版 0.1.7。此文档只整理已有产品与下一步验证方案，不启动版本迭代。`已实现`、`已做代码/合成测试`、`待实测`、`方案`是不同状态；任何示意数字都不代表实际录取率或已取得的业务结果。

## 1. 产品定义与问题

**一句话定位：** 让准备申请香港、新加坡授课型硕士的学生，把自己的背景与项目官方资料、已审核的公开成功案例放在一起比较，获得有证据边界的项目机会参考，并自行决定申请顺序。产品不是学校官方录取系统、留学中介，也不代替申请决定。

**用户任务：** 在申请时间、费用有限时，找出值得投入的项目；弄清“为什么适合/不适合”“资料哪里不足”“哪些结论来自官方要求、哪些只是案例观察或模型推断”。仅有“专业匹配”之类泛泛文字不够；孤立的百分比也不能满足可信决策。

**核心体验（已实现）：** 填写本科院校、专业、成绩及可选经历 → 选地区/方向 → 获得候选项目分析 → 看项目要求、案例分布、模型机会参考值和区间 → 按参考值从高到低比较 → 查看依据并导出。可在同一桌面程序中指定具体项目采集公开案例，审核通过后供后续分析使用。反馈问卷可选，下载不以填写问卷为条件。详见 [产品说明](../PRODUCT.md)、[迭代记录](iteration-2026-10-13.md) 与 [界面](../index.html)。

| 用户故事/需求 | 优先级 | 当前验收依据与缺口 |
| --- | --- | --- |
| 我想比较多个目标项目，而非只听笼统建议 | P0 | 参考值降序、并列、缺值置后有本地测试；真实排序质量未测 |
| 我想知道每条判断依据及其局限 | P0 | 展示官方快照/成功案例、范围与未校准提示；引用事实正确性待人工标注 |
| 我想让稀有项目即使没有案例也得到谨慎分析 | P0 | 允许零案例路径；真实模型的零案例质量待测 |
| 我想指定某个项目去找公开案例 | P1 | 指定范围与完整项目目录有代码/打包测试；真实联网验收待做 |
| 我想了解和控制个人 API 花费 | P1 | BYOK、部分采集预算存在；完整逐报告 Token 账本尚未实现 |

**本阶段不做：** 真实录取率承诺、保底/冲刺自动分层、雅思小分自动达标判断、实时全网官方要求核验、付费代申请或无人工审核地把抓取内容提升为事实。

### 为什么使用 AI，而不是只做规则表？

申请人的专业、课程、实习和项目经历是非结构化且中英混合的；公开案例与项目介绍也有不同写法。AI 适合做候选项目的语义筛选、从公开页面抽取字段、把申请背景与项目要求及案例结合为可读解释。仅靠关键词或固定打分表难以覆盖跨专业与别名表达。

但 AI **不应独自决定事实**：GPA 原始分制保留、同分制案例统计、证据来源区分、语言**总分**条件检查、项目 ID 对齐、输出格式和证据引用校验由本地规则处理。AI 的优势是处理开放文本，不是拥有录取委员会数据；它输出的数字不是统计模型测得的录取频率。分析阶段读取本地项目与案例快照，并向用户配置的模型 API 发送上下文，**不会在每次分析时自动上网核验官网**；案例采集是另一条联网流程。[方法边界](../METHODOLOGY.md)。

## 2. 范围、流程与架构

当前交付物是用户自配 API 的 Windows 便携桌面程序，不是继续运营的公共网页版。Electron 界面连接只监听本机的服务；申请数据、分析记录、反馈与案例审核数据保存在本机 SQLite；用户提供 HTTPS Chat Completions 完整接口地址、模型名和 API Key，Key 由系统安全存储加密后保存在本机。**请求中的申请背景和检索证据仍会发往用户选择的模型服务商**，不能把“本机运行”表述为“所有数据从未出机”。[桌面入口](../desktop/main.mjs)、[记录结构](../collector/store.mjs)。

```text
申请分析：申请资料 → 本地候选召回 → 第一层模型筛选项目
          → 读取官方资料快照 + 已审核成功案例 → 第二层逐项目模型判断
          → 横向参考值校准/对齐 → 证据契约与规则校验
          → 数值/区间/案例量/不确定性展示与降序比较

案例采集：用户指定项目 → 白名单来源与搜索 → 页面解析/必要时模型抽取或 OCR
          → 去重/项目映射/来源核验 → 待审核 → approved → 下次分析读取
```

这是“检索增强 + 两阶段模型分析 + 确定性校验”的应用架构，**不是模型微调，也不是本地训练的录取率预测器**。桌面分析对逐项目请求最多并发 2 个，再运行横向校准；此前用户实测 8 项目仅 2 项有数值，原因包括服务商并发限制和证据契约失败，不能归因为案例不足。[桌面调用](../desktop/legacy-analysis.mjs)、[故障复盘](iteration-2026-10-13.md)。

**失败与边界：** 零案例项目仍可结合可用项目资料尝试分析，但应扩大不确定性并明确缺失证据；模型调用、格式或证据校验失败时可显示“暂无数值”和具体原因，不能用本地公式伪造补位。排序只针对同一申请背景下通过校验的**模型参考值**；无数值排后、并列共享名次。没有“冲刺/保底”自动分层，也不能把排序等同于真实概率差异。语言只判同考试类型的总分；雅思/托福小分及其它完整条件须用户核对当年官网。[比较逻辑](../comparison.mjs)。

**当前尚未证明：** 指定项目采集入口和打包目录已有代码与测试，但未完成真实联网采集、真实 API、真实用户操作的端到端验收；也没有实测跨服务商兼容性。项目官网资料是带日期的本地快照，不是实时官方保证。

## 3. 为什么选这个模型？现状不是“选定唯一模型”

**真实现状：** 软件允许用户填写兼容 Chat Completions 的服务商及模型名，未固定生产模型，也没有同批样本的模型对照实验。因此不能在简历/PRD 中写“通过评测证明某模型最优”。截图里曾使用 DeepSeek，只能说明它是配置或候选示例，不能倒推整个产品始终使用它。当前实现要求服务商接受 `response_format: json_object`，部分请求还带 `thinking` 字段；所谓“兼容”须以真实连接和完整报告测试为准。[API 设置](../desktop/main.mjs)、[实际请求](../desktop/legacy-analysis.mjs)。

**选择逻辑（待验证的模型决策框架）：**

| 维度 | 产品需要的能力 | 验证方式 |
| --- | --- | --- |
| 正确性 | 中英混合资料理解、项目名称/专业别名识别、官方硬性条件不误读 | 同一批人工标注场景的事实、召回和硬条件误判 |
| 可控性 | 稳定输出 JSON、遵守证据 ID、信息不足时保留不确定性 | 有效输出率、引用支持率、拒答/无数值比例 |
| 体验 | 多项目完成率、P95 时延、服务商限流稳定性 | 真实 API 批量跑同一组输入，记录失败原因 |
| 成本与隐私 | 每份报告 Token/费用可控，数据出机边界可告知 | 读取 API `usage`、价格表和服务条款 |

以 DeepSeek 为**候选方案**而非已经评测胜出的选择：其官方文档列出 Chat Completions 兼容接口和 JSON Output；`deepseek-flash` 比 `deepseek-v4-pro` 标价更低，适合做成本基线，Pro 可作为质量对照。以上是接口和标价层面的选择理由，**不是本项目已证实的分析质量或中文准确率优势**。模型名、能力、价格都可能变动，实际使用前应看[官方模型与价格](https://api-docs.deepseek.com/quick_start/pricing/)及[Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)。不应为求简历叙事而虚构“自主选型优于其他模型”的结果。

## 4. 是否搭建了数据集？搭建了证据库，未搭建可校准的录取结果集

现有打包快照（只说明该快照，不代表当下全部港新项目或实时官网）包含 **3,435 条已审核成功案例、832 个项目卡片、7,672 条项目证据记录**；数字来自本地 `build/desktop-seed` 的 JSONL 行数。桌面案例库入包规则为 `approved`、2021 年及以后、能对应项目，项目文档只选有内容的官方来源类别。采集新案例可进入待审核队列，只有审核通过才进入分析；同一用户本机数据库可能与打包快照不同。[打包脚本](../scripts/build-desktop-seed.mjs)、[案例审核规则](../collector/store.mjs)。

这些资料可称为“**本地项目与公开成功案例证据集**”，不能称为“用于训练并验证录取概率的完整监督数据集”。它缺少同条件申请但被拒的样本、真实申请分母和均衡抽样，公开成功案例还存在主动分享偏差；部分字段和官方条件也未完整覆盖。因而现在既没有模型微调，也不能从成功案例比例推导真实录取率。若未来要做概率校准，必须合法获得成功与失败结果、固定训练/验证/测试划分并按项目与申请年份检查偏差；在此之前页面只能叫“**模型机会参考，未经统计校准**”。

## 5. 评价体系、反馈与 Bad Case 闭环

**现状区分：** 已有单元/契约测试、排序及边界回归，以及 50 条**合成**语言声明防护测试；这不能换算成 Agent 的事实准确率。已实现本机分析记录和自愿反馈：有用程度、最有价值部分、理解清晰度及选填意见；尚无真实用户满意度样本或完整模型效果基线。[评测边界](../eval/README.md)、[反馈界面](../index.html)、[记录结构](../collector/store.mjs)。

**评测方案，尚待执行：** 冻结同一批至少 50 个覆盖普通、零案例、跨专业、资料缺失、官方条件冲突、旧快照、服务商限流等类型的场景。每条保存脱敏申请输入、项目/证据版本与抓取日期、模型及参数、原始请求/响应、展示结果、耗时、Token 和人工正确答案；先测现状 V1，再在同样条件下测候选 V2。可以用官方资料造测试场景，但必须标记“合成”，不能当真实用户结果。标注至少双人复核争议项，原文无法确认的标“不可判定”，不硬算作正确。

| 层次 | 指标与口径 | 当前状态 |
| --- | --- | --- |
| 数据/检索 | 项目召回率＝正确召回项目数/应召回项目数；资料覆盖与时间戳；错项目映射数 | 待基线 |
| 事实/证据 | 事实准确率＝正确可核验判断/全部可核验判断；引用支持率＝被来源支持的引用判断/可核验引用判断 | 待人工标注 |
| 安全边界 | 硬性条件误判率、伪造证据 ID 率、无资料仍装作确定的比例；该拒答时是否拒答 | 已有部分规则测试，端到端待测 |
| 稳定性 | 完整报告率、逐项目有数值率、失败原因分布、P95 时延、重试/限流率 | 只有个别用户故障记录，非总体统计 |
| 决策有用性 | 同背景项目排序一致性、改进一个条件后的反事实合理性、用户能否解释排序和做选择 | 待场景实验；不等于概率校准 |
| 经济性 | 每份报告输入/输出 Token、成本中位数和 P95、每条获批新案例成本 | 待完整计量 |

**Bad Case 流程：** 用户可自愿标记“来源不对/项目没找全/把条件读错/数值不可信/响应失败/看不懂”；产品侧脱敏保存复现 ID → 归类为数据缺失或过期、检索漏召、项目映射、模型事实误读、引用不支持、证据契约、提供商错误、界面误导 → 对照来源原文定位根因 → 仅修一类问题 → 在冻结集与原坏例上回归，记录改前/改后。申请资料敏感，不应默认上传原始案例或用户信息做共享评测。原始日志、用户反馈与人工标注必须分开，问卷评分不能替代客观正确性。

**验收门槛（方案，非已达成结果）：** 基线报告必须给出上述指标的分母、样本构成、缺失值、错误类别与成本分布；若出现“未满足明确官方硬门槛却声称完全达标”或“引用不存在的来源”，应列为阻断性 Bad Case；模型替换必须在相同资料快照、相同样本和价格日期下比较。真正的“65% 预测是否对应约 65% 录取”，只有获得代表性的成功+失败结果后才评估校准曲线和 Brier Score；目前该项明确为**不可测**。

## 6. 商业模式与 Token 经济性

**当前交易模式：** BYOK（用户自行提供并支付模型 API），软件不代收模型费、没有已验证的付费转化或盈利数据。这个选择把首次交付的服务端推理支出转给用户，同时使成本与隐私告知更重要；它不是“免费使用 AI”。用户仍承担供应商费率、限流与隐私条款风险。未来可测试一次性桌面授权或面向顾问/学校的专业版，但价格、付费意愿、数据授权和合规都未验证，不写成既成商业成果。

**商业假设（不是上线收入）：** 对个人用户，价值是减少搜集/对照项目资料的时间与决策盲点，可能考虑一次性软件授权；对顾问机构，价值可能是批量、可追溯的初筛和审核工作台，但会增加权限、数据治理与服务成本。两条路径都需先验证用户是否愿付费、是否信任未校准的参考值、能否接受 BYOK 的设置门槛，以及平均支持成本。BYOK 模式下软件方不直接承担模型 Token 账单，但并非没有开发、分发、维护与合规成本；若未来改为平台统一付费，毛利需按“收入－推理/搜索/OCR－支付－服务与获客成本”另行测算。

**分析一次的调用路径：** 候选项目卡片分批筛选（当前每批最多 8 个，失败可能重试；不确定项目可能再次完整复核）＋每个入选项目 1 次分析（最多 8 项，同时最多 2 个）＋最后 1 次横向校准。实际调用数取决于候选数、筛选结果、失败与重试，**不是每份报告固定 1 次 API**。单次请求设置 `max_tokens` 上限（当前默认 4,000）只约束输出上限，不代表实际输出量或总账单；项目请求中还包含申请背景、项目对照信息和所选证据，因此输入 Token 可能较大。[调用实现](../desktop/legacy-analysis.mjs)。

**采集一次的调用路径：** 搜索规划、页面抽取、必要的项目名映射/OCR/关键字段复核都可能调用模型；结构化解析、缓存命中或预筛跳过则可减少调用。页面上“搜索请求预算”是网络搜索预算，服务端的 `max-api-calls` 主要约束抽取计数，**不能把它当成采集全部模型请求或总 Token 的硬封顶**。采集运行报告已有部分阶段的 `usage`/Token 字段，但桌面分析的模型响应当前只解析内容，未形成完整逐阶段 Token/费用账本。任何“每份报告成本 X 元”的现成数字都缺乏依据。[采集流程](../collector/agent.mjs)、[服务端默认预算](../server.mjs)、[采集配置](../review.html)。

**核算公式：** 单次成本＝Σ阶段〔非缓存输入 Token ×该模型输入单价＋缓存命中输入 Token ×缓存单价＋输出 Token ×输出单价〕÷1,000,000；若供应商另计图片、搜索或其它费用，应再加上。按筛选、逐项目、校准、搜索规划、抽取、OCR、复核分别记录 `request_id`、模型、成功/失败、`usage.prompt_tokens`、`usage.completion_tokens`、缓存量、费率版本和归属报告/采集批次。限流失败请求是否计费依服务商账单核对，不凭推测归零。可优化的不是盲目删证据，而是缓存重复资料、先规则筛页再调用模型、控制候选上限、把低成本模型用于简单抽取、限制输出并观察质量回退。

DeepSeek 官方价格表按每百万 Token、缓存命中/未命中及峰谷时段计费，且可能调整；如要算示例，应**代入实际 `usage` 与调用日期的价格**，不能把示例 Token 写成真实运行成本。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)。

## 7. 可展示的产品判断与未完成事项

| 用户发现与取舍 | 已有证据 | 不应夸大的部分 |
| --- | --- | --- |
| 隐藏百分比损害跨项目决策；保留数值但加范围、案例量、未校准提示 | 结果展示、排序规则与回归测试 | 不是校准后的真实录取率 |
| 8 项目仅 2 项有数值时追查失败记录，再把并发设为 2、校准延后 | 真实故障复盘及代码调整 | 不是总体完成率提升数据 |
| 发现项目卡片空字段而本地有官方快照，修复展示链路 | 来源字段与测试 | 快照不等于实时官网 |
| 数据库缺完整小分门槛，主动不做错误的“已达标”判断 | 语言总分边界与回归 | 不能宣称判断完整语言资格 |
