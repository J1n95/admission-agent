# 录取参照：量化参考与项目对照迭代记录（2026-10-13）

本记录用于后续项目复盘、简历筛选和面试准备。记录的是本轮已核对的产品判断、代码改动与验证，不把设计示意、合成测试或模型估计写成真实录取结果。当前交付对象为用户自填模型 API 的 Windows 便携版，不是公共网页版。

## 1. 问题从哪里来

此前结果页已有模型生成的项目百分比和范围，但默认隐藏数值。这样虽然避免了把未经校准的数字误称为录取率，也削弱了用户比较多个项目、分配申请时间和预算的核心用途。用户明确指出：申请者需要知道几个目标项目中哪个更值得优先申请，而不只是看到“专业匹配、竞争激烈”这类描述。

同时，公开案例主要是成功案例，缺少同等条件下的拒录样本。因此模型输出的 `65%` 不能解释为“相似申请人申请 100 次会录取 65 次”。原方案若只展示精确整数，也容易造成虚假的统计确定感。

另一个现场问题是某项目结果页显示“要求/定位/课程未补齐”。检查本地数据后发现，项目卡片相应字段为空，但证据库已经存有带日期的官方资料结构化快照；桌面结果页没有使用这些已有字段。这是展示链路断层，不等于项目资料在本地完全不存在。快照也不等于今天已复核官网。

## 2. 用户推动的关键产品判断

| 判断 | 理由与取舍 | 本轮决定 |
| --- | --- | --- |
| 保留百分比 | 申请人需要跨项目的量化参考，直接删除会损害核心用途；但没有成功/失败结果数据，不能宣称其为真实录取率。 | 默认显示**原有模型参考值**，紧贴范围、案例量和“未校准”提示；不新增人工概率公式。 |
| 从单项目数字转向项目比较 | 用户希望自己判断申请组合，不需要系统额外代做冲刺、重点或保底分层。 | 仅按同一申请背景下的模型参考值降序排列并显示相对名次。 |
| 暂缓雅思小分 | 现有项目数据库没有完整、可核验的小分门槛；只加一个最低小分输入无法可靠判断每个项目是否达标。 | 不新增小分输入、门槛判断或资料库重抓；语言要求仍须核对官网。 |
| 做小范围验证 | “排名合理”与“百分比概率准确”是不同命题。 | 先检查本地排序、并列、零案例与无效输出的边界；真实模型反事实测试和概率校准均未完成。 |

其中，截图中的 `35% / 48% / 68%` 等数字只是讨论界面的示意，**不是本项目的测试结果或实际模型输出**。

## 3. 实际实施

1. 结果页不再用按钮默认隐藏模型数值。每个通过校验的项目显示百分比、参考范围、公开成功案例数、相对名次；缺失或未通过校验的项目不显示数字。详情和导出摘要均保留“未经统计校准，非真实录取率”的说明。入口见 [`app.mjs`](../app.mjs) 的 `renderResults`、`downloadReport` 与 [`index.html`](../index.html) 的结果区域。
2. 增加同一申请背景下的项目排序：有数值的项目按模型参考值从高到低排列，无数值项目置后，并列数值共享名次。系统不再代替申请人划分冲刺、重点或保底。规则见 [`comparison.mjs`](../comparison.mjs)。
3. 为有模型个性化结论的项目显示一条匹配线索；没有通过校验的结论不补写理由。页面提醒：参考区间重叠时，不能断言两项目的真实机会有差异。
4. 对卡片空字段，只回填本地证据库中 `official` 或 `official-structured` 的对应快照；不覆盖已有卡片内容，也不把 `derived-ai` 推断提升为官方事实。详情页标注快照日期和“未复核当前官网”。链路见 [`desktop/legacy-analysis.mjs`](../desktop/legacy-analysis.mjs) 的 `displayProgramme` 与 [`app.mjs`](../app.mjs) 的 `renderProgrammeDetail`。
5. 同步更新 [`README.md`](../README.md) 与 [`METHODOLOGY.md`](../METHODOLOGY.md)，将“默认隐藏数值”的旧描述改为当前行为，并说明零公开案例也可尝试模型分析，但信息边界更大。

## 5. 尚未完成，不能写成成果

- **百分比校准**：没有足够的真实成功与失败申请结果，不能验证“60% 是否真的对应约 60% 录取”。
- **模型排序稳定性**：尚未用真实模型 API 做同一申请人仅改雅思 6.5→7.5 等前后对照实验；本轮测试只验证本地展示与排序规则。
- **官方条件实时性**：项目资料是本地快照，不是每次分析实时联网复核。雅思小分门槛未系统收录，不能宣称自动判定达标。
- **用户效果**：未完成真实用户实验，不得写“准确率提升”“申请成功率提升”“用户满意度提升”等数字。
- **发布状态**：只完成本地 Windows ZIP 构建；本轮没有上传 GitHub 或公开发布新版。

## 6. 以后如何如实讲述这次迭代

用户主导的判断是：指出隐藏百分比损害核心决策用途；坚持保留量化比较；识别当前数据库缺少雅思小分条件，主动缩小范围；要求在可信度与实际可用性之间做权衡。Codex 负责本轮代码实现、测试、文档和打包。面试可以讲自己的问题发现、需求权衡、验收思路以及如何审查 AI 协作产出；不要把 AI 辅助开发表述为完全独立编码。

可核实的项目表述：**“针对申请评估中数值可信度与跨项目比较的冲突，保留未校准模型参考值，并补充区间、案例量、相对排序和信息边界；发现项目卡片与本地官方资料快照的展示断层，推动修复并建立边界测试。”** 若将来完成真实模型/用户实验，再另外补充实测方法和结果。

## 7. 实测反馈后的第二次修正

用户使用 0.1.2 分析 8 个项目时，只有 2 个项目显示数值。读取本机保存的该次分析记录后确认：5 个项目调用及横向校准调用被模型服务商以账户并发超限拒绝，另有 1 个项目的模型输出没有通过证据契约；这与项目分别拥有 8、29、43、62 条公开成功案例无直接关系。

据此完成 0.1.3 修正：项目模型调用并发上限改为 2，横向校准在项目调用结束后单独执行；无数值时显示并发受限、请求超时或证据校验失败等简明原因；删除用户认为多余的申请分层，只保留模型参考值、区间、案例量和降序排列。该次修改再次体现了“根据真实运行记录定位原因，而不是把失败笼统归为数据不足”的迭代方式。

## 8. 恢复“只判断语言总分”的产品边界

0.1.3 的港科大电子工程结果因证据契约未通过而没有数值。复查发现，代码仍会识别项目资料中的雅思单项门槛，并在申请人未填写小分时阻止模型声称语言达标；这与此前“暂不采集、暂不判断小分”的产品决定不一致。0.1.4 将语言确定性检查恢复为只比较同考试类型总分，单项要求不再阻断项目判断；结果页同步改为“总分已达到/未达到，当前版本不判断单项分数”。整体语言要求仍需申请人自行核对官网。

## 9. 将案例采集接入同一桌面程序

用户希望此前独立运行的公开案例采集 Agent 与申请分析共用一个 EXE。复查发现，项目已有采集、状态查看和审核页面，但桌面版隐藏了这些入口，采集脚本也把运行日志、锁和缓存写在源码目录；打包后该目录只读。另外，桌面分析只读打包时的案例快照，即使采集成功，新增案例也不会自动进入分析。

0.1.5 复用现有采集与人工审核流程，在程序菜单增加“案例采集与审核”；桌面本地令牌允许该窗口访问采集接口，仍拒绝未持令牌的外部请求。采集脚本和子进程改为使用本机用户数据目录写入缓存、日志和 SQLite，打包时携带来源白名单及项目别名配置。界面默认只尝试 3 个项目、单并发，并在启动前提示访问外部网页与模型 API 的费用。分析时重新读取本机数据库：只有 `approved` 且 2021 年及之后的案例可进入证据，`pending` 不进入，原有案例如被驳回也应退出分析。相关实现见 [`desktop/main.mjs`](../desktop/main.mjs)、[`server.mjs`](../server.mjs)、[`collector/agent.mjs`](../collector/agent.mjs)、[`collector/expansion-agent.mjs`](../collector/expansion-agent.mjs) 与 [`desktop/legacy-analysis.mjs`](../desktop/legacy-analysis.mjs)。

验证边界：本地测试检查了桌面令牌隔离、审核页面可访问、新增 approved 案例进入下一次分析、pending 排除、已驳回案例退出；采集 CLI 在打包后的 EXE 下以只读 `status` 模式启动并创建了隔离的测试数据库。未执行真实联网采集或真实模型 API 调用，因此不能宣称已经实测抓取成功率、资料覆盖率或模型费用。

## 10. 入口可发现性修正

用户打开 0.1.5 后截图指出：主页面顶部只有“基础信息 / 申请评估”，看不到案例采集。核对运行进程确属 0.1.5；原因不是用户打开旧版，而是实现只在 Windows 原生程序菜单加了入口，没有在页面内提供可见入口。0.1.6 在页面右上角加入“案例采集与审核”链接，保留原有菜单入口；桌面本地令牌仍保护采集与审核接口。此处是交付可发现性问题，不能把“后台功能存在”当成用户能找到并使用的完成标准。

## 11. 让用户指定采集项目，并修复项目目录漏打包

用户在 0.1.6 采集页看到“主表项目 25 个、24/25 已达标”，认为这不可能代表港八新二全部项目，并明确提出：主要需求是**指定某些具体项目，只采集它们的公开录取案例**。核对发现，源码可读取 832 个有效港新项目，但桌面打包配置排除了 `collector/data/programme-catalogue.json`；`master-data.mjs` 又在读取失败时静默回退到 25 个预置项目，导致采集范围和“全部项目”覆盖标题失真。这里的 25 是项目数，不是案例数；“项目方向”只是按项目名称推断的粗标签，不应替代用户直接选项目。

0.1.7 在案例审核页增加按学校或项目名称搜索、逐个添加和移除项目的入口。明确选中具体项目时，仅这些项目进入采集计划；地区、学校、方向和默认“项目尝试上限”不再隐式截断该名单，同时禁止全站 Mastermate 索引导入。自动采集仍保留原有目标数与请求预算：达到目标的项目跳过；此前因多轮无进展而自动排除的项目，用户明确指定时可再尝试一次，未选中的项目仍遵守原规则。对应入口与流程见 [`review.html`](../review.html)、[`review.mjs`](../review.mjs)、[`server.mjs`](../server.mjs)、[`collector/expansion-agent.mjs`](../collector/expansion-agent.mjs) 和 [`collector/agent.mjs`](../collector/agent.mjs)。

打包配置现携带完整项目目录；运行时优先读取源码目录，若打包后不存在，则读取 EXE 附带资源，资源也缺失时不再悄悄展示 25 个项目。见 [`package.json`](../package.json) 与 [`master-data.mjs`](../master-data.mjs)。单元测试验证指定项目不扩展到其他项目、桌面接口提供超过 100 个项目以及打包配置包含目录文件；已构建 0.1.7 ZIP 并检查其包含目录文件。**未执行真实联网抓取、真实模型 API 调用或用户操作测试**，因此不能声称选定项目已经抓到新案例，下一步需在隔离数据目录做小规模实测。

## 12. 模型对比入口的可发现性修正

0.1.9 将千问与 DeepSeek 的加密配置和 30 次受控模型对比接入桌面设置窗口。用户打开软件后反馈找不到 API 设置入口。检查发现设置窗口虽然可从 Windows 应用菜单打开，但主页面没有可见入口；这是交付后的操作路径问题，而非模型 API 本身的问题。0.1.10 在主页面右上角增加“模型 API 设置”按钮，通过仅提供打开设置权限的桌面桥接调用现有窗口，同时保留应用菜单与快捷键。普通浏览器页面不展示该按钮。验证包括代码检查、打包内容检查和离线启动；真实模型调用仍待使用新 Key 的实测。

## 13. 首次真实模型对比与 0.1.11 复测

2026-10-16 首次用同一批 15 个固定场景分别调用千问 Flash 和 DeepSeek Flash，共 30 次。原始记录位于本机 `model-ab/2026-10-16T10-36-48-499Z-528a84bc`，费用按服务商返回的 token 用量与保守单价估算约 0.4412 元，非账单。首次程序结构通过率分别为千问 10/15、DeepSeek 14/15；双方都在电子工程筛选场景达到 3000 输出 token 上限并截断。千问有 4 个单项目输出未通过，主要涉及证据引用格式；另发现语言声明校验会误判“需满足语言要求”这类一般性说明。双方虽通过全部排序结构检查，理由仍各有一处不可能的名次表述（“第19位，共18人”“rank 12/11”）。**这些是模型输出与校验行为的实测，不是录取准确率。**

用户提出“Flash 是否过弱”和“希望 API 返回不要截断”，并要求修订后复测。0.1.11 将筛选、单项目分析、排序的输出上限分别改为 6000/5000/4000 token，修正提示词中与 `[documentId]` 契约矛盾的 JSON 示例，修复上述语言校验误判，并将明显不可能的名次单列在人工评分表中。当时曾增加按模型和场景排列的 Markdown 阅读版；用户随后澄清不需要该文件，只要求模型 API 调用不发生截断，因此当前已移除该额外导出和设置页提示，完整原始响应仍保存在 `results.json` 的 `rawOutput` 字段，并以 `finishReason` 记录服务商是否因长度停止。代码见 [`eval/model-ab.mjs`](../eval/model-ab.mjs)、[`miniprogram/cloudfunctions/admissionApi/agent/runtime.mjs`](../miniprogram/cloudfunctions/admissionApi/agent/runtime.mjs)、[`assessment-contract.mjs`](../assessment-contract.mjs) 及两份同步的 `assessment-system.txt`。

同日复测仍为 30 次真实调用，记录在本机 `model-ab/2026-10-16T11-27-50-556Z-8884a7f3`。筛选 8/8 不再截断；DeepSeek 15/15 结构通过；千问当时仅 8/15，其中 7 个单项目理由均把允许的证据 ID 放在行首，却没有方括号。经核对，这些 ID 均来自本轮 `evidenceSelection`，因此将解析器限定为**只对证据清单中的开头 ID**补成 `[documentId]`，不接受陌生 ID。使用已保存输出和相同资料离线复核后，两家均为 15/15 程序可接收；复核结果另存 `离线复核.json`，原始记录不改，也没有为这一步再次调用模型。复测费用估算约 0.4419 元，两轮合计约 0.8831 元；实际账单仍待核对。

验收边界：15/15 只是当前结构契约通过，不是事实准确或模型能力相同。项目筛选所用参考集与整体排序参考顺序是临时人工标签，不能证明真实录取机会。初步抽查复测原文发现，千问在多个单项目报告中仍写出“GPA 3.85（约85+）”“GPA 3.47（约87.5%）”等跨分制近似换算，和提示词的分制规则冲突；这不因引用格式被规范化就消失。DeepSeek 未在同批报告中出现同样字面模式，但仍未完成逐条事实核验。下一步先用同一批输出核对官方原文和案例，再决定是否用更强千问模型做少量困难场景的增量实验；不能把本次结果写成“多个模型效果已验证最优”。

## 17. 案例位置口径修复（2026-10-17）

比较三模型原始排序输出时发现，共用输入中若申请人的等效分低于全部 18 条可换算成功案例，原统计按“插入样本后的相对位置”计算 `rank=19,total=18`。作为插入位这个计算有意义，但模型和评测读者容易把它说成“在 18 条案例中排名第 19”；旧评测的明显错误名次检测也未识别“在18例案例中排名第19”这一自然语言形式。另有模型把成功样本最低分说成硬门槛、在官方语言门槛未收录时宣称语言达标。原因分别是数值字段缺少语义区分，以及提示词对样本边界和语言核验的禁止性表述不够直接。

在桌面版与小程序版共用的案例分析统计中，低于全部可比成功案例时不再输出超出 `total` 的 `rank`，而输出 `rank=null` 与 `positionNote="低于全部 N 条可换算公开成功案例；案例最低分不是官方录取门槛。"`；范围内仍保留合法的插入位置以兼容展示。桌面结果页将范围内位置明确称作“若插入”的位置，并说明低于样本最低分不等于不符合官方门槛。两份单项目提示词和两份横向排序提示词同步明确：不得把超出样本的插入位写成案例名次、不得把成功样本最小值当作录取线、官方总分门槛未知时不能声称语言达标。评测检查补充识别自然语言中的“在 N 条案例中排名第 N+1”。相关实现见 [`case-analysis.mjs`](../case-analysis.mjs)、[`app.mjs`](../app.mjs)、[`prompts/assessment-system.txt`](../prompts/assessment-system.txt)、[`prompts/probability-calibration-system.txt`](../prompts/probability-calibration-system.txt)、[`eval/model-ab.mjs`](../eval/model-ab.mjs) 及小程序镜像文件。

离线回归覆盖低于全部案例、与最低案例同分、超过最高案例以及桌面/小程序统计一致性；模型评测测试覆盖旧报告里的自然语言异常名次。此修复只改变统计字段解释、用户文案与提示词，不改公开案例、GPA 换算、模型参考百分比计算或旧盲测原始结果；未调用付费模型。提示词约束能降低误读风险，但没有新一轮模型输出，因此尚不能声称模型生成内容已经改善。
